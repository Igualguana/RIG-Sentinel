# Audit Foundation (Genesis B2-M2-B)

> **Status: development, unreleased.** M2-B is the pure, in-memory foundation of the audit
> subsystem. It is **not** a complete or production audit log:
> - there is no persistence, cross-event ordering chain, checkpointing, key storage or rotation (M2-C);
> - nothing yet evaluates and audits in one step, and there are no failure modes (M2-D).
>
> The API and schema may change.

`rig_sentinel.audit` builds privacy-minimized, versioned **audit events** from M1 policy
decisions, optionally authenticates them, and can keep them in process memory. Events record
**decisions**. They never claim that a tool ran, that a decision was enforced
(`"enforced": false` always), or that an event was saved.

## Architecture

```text
caller ──▶ PolicyEngine.evaluate(request) ──▶ DecisionRecord          (M1, unchanged)
   │                                               │
   └── same request object ──▶ AuditEventBuilder ◀─┘
                                 │  re-parse request with M1's parser; compare request_digest
                                 │  redaction: kind/depth + HMAC refs (K_ref) or nothing
                                 ▼
                              AuditEvent (frozen, closed schema, validated on construction)
                                 │  AuditEnvelope.seal(event, K_auth | None)
                                 ▼
                              AuditEnvelope ──▶ MemorySink.append() ──▶ AuditReceipt
```

| Module | Responsibility |
|---|---|
| `events.py` | Frozen models, the `rig.audit-event/v2` event, the `rig.audit-envelope/v1` envelope, and envelope sealing and verification |
| `builder.py` | `AuditEventBuilder`: `DecisionRecord` + original request → event or envelope |
| `redaction.py` | Resource minimization, keyed references, credential-like identifier filter, `error_type` mapping |
| `validation.py` | Field checks and closed-schema parsers for untrusted dictionaries |
| `chain.py` | Canonical digests, HMAC-SHA-256, pseudonyms, constant-time comparison, `AuthStatus` |
| `keys.py` | `AuditKey` and `AuditKeys`: in-memory keys with purpose binding |
| `sinks.py` | `AuditSink` protocol, `MemorySink`, `AuditReceipt` |
| `errors.py` | `AuditError` and closed `AuditErrorCode` values |

**Dependencies:**
- `rig_sentinel.audit` depends on `rig_sentinel.policy`, and `rig_sentinel.policy` never imports `rig_sentinel.audit`.
- The package uses the standard library only (`hmac`, `hashlib`, `secrets`, `json`, `threading` in `sinks.py`), with no file, database or network I/O.
- `tests/test_audit_isolation.py` checks all of this.

Envelope sealing and verification live in `events.py`, next to the envelope model; `chain.py` holds only the primitives. This avoids an import cycle.

## Event schema

One envelope:

```json
{"envelope_schema": "rig.audit-envelope/v1",
 "event": { "schema_version": "rig.audit-event/v2", "audit": {}, "engine": {}, "caller": {} },
 "event_digest": "<64 hex: SHA-256('rig.audit-event/v2' NUL canonical(event))>",
 "auth": {"algorithm": "HMAC-SHA256", "key_id": "<32 hex>", "mac": "<64 hex>"} | null}
```

Every object has a closed field set: unknown or missing fields are rejected, and absent values are explicit `null`.

### Fields by provenance

| Section | Fields | Source |
|---|---|---|
| `audit` | `event_id`, `correlation_id` (128-bit random hex), `recorded_at` (UTC, µs), `redaction_mode` (`scoped` or `no-ref-key`), `ref_key_id` | Generated by the audit layer |
| `engine` | `decision`, `reason_code`, `decision_ref` (= the record's `decision_digest`), `protected`, `enforced` (must be `false`), `record_schema`, `engine_version`, `evaluated_at`, `policy_id`, `policy_version`, `policy_sha256`, `deciding_rule_ids`/`_count`, `matched_rule_ids`/`_count` (first 32 + total), `approval`, `error_class`, `request_digest` | One detached snapshot of the M1 `DecisionRecord` (see below), accepted only if its `decision_digest` recomputes from that snapshot |
| `caller` | `consistency`, `agent_id`, `assurance_claim`, `tool_id`, `manifest_sha256`, `operation`, `environment`, `labels`, `resource` {`kind`, `depth`, `authority_ref`, `resource_ref`}, `session_ref`, `request_ref`, `redacted_fields` | **Claims made by the caller.** Not authenticated by anyone |

**`caller.consistency`:**
- `consistent`: the request object passed to the builder re-parses (with M1's own parser) to the record's `request_digest`. This proves the recorded fields are the ones that were evaluated. It does **not** prove who the caller is, so the value is never called "verified".
- `invalid_request`: the request doesn't parse.
- `mismatch`: it parses to a different digest (changed after evaluation, or a hostile object).
- `not_applicable`: the record has no `request_digest`, for example policy unavailable.

In every state except `consistent`, all caller fields are `null`.

**Never recorded:**
- raw requests, tool arguments, prompts, credentials, Authorization headers;
- exception messages, untrusted exception class names;
- raw session or request ids;
- persistence status.

## Privacy defaults

| Data | `scoped` (K_ref present) | `no-ref-key` (no K_ref) |
|---|---|---|
| Resource | `kind`, `depth`, `authority_ref` = HMAC(K_ref, authority), `resource_ref` = HMAC(K_ref, canonical resource) | `kind` and `depth` only; no authority, no reference |
| `session_id` / `request_id` | `session_ref` / `request_ref` = HMAC(K_ref, id) | Omitted |
| `agent_id`, `tool_id`, `labels` | Stored as is (policy vocabulary), unless they look like credentials | Same |

- **Pseudonyms** are HMAC-SHA-256 under `K_ref`, cut to 128 bits, with a separate namespace per kind (`rig.audit-ref/v1/session`, `…/resource/db`, …). **Unkeyed SHA-256 is never used as a pseudonym**: guessable values such as paths, tables and hosts could be brute-forced from it.
- **No full-identifier mode** exists in M2-B.
- **Credential-like identifiers** (known prefixes such as `sk-`, `xoxb-`, `glpat-`, or long mixed letter-digit runs) are dropped and counted in `redacted_fields`. This is a heuristic and only a second line of defense.
- **`redacted_fields` is an exact count**, never saturated. At most 1 (`agent_id`) + 1 (`tool_id`) + 32 unique labels (M1's `MAX_REQUEST_LABELS`; `parse_request` rejects more) = 34 redactions are reachable, below the schema bound of 64. A test fails if M1's label limit ever grows past that bound.
- **`error_class`** is a built-in exception name, `UnlistedError` or `InternalError`. Anything else maps to `UnlistedError`.

## HMAC design and limitations

- **Two independent keys:**
  - `K_ref` (purpose `ref`) for pseudonyms;
  - `K_auth` (purpose `auth`) for envelopes.

  Both are 32 bytes from `secrets.token_bytes`, or supplied as exactly 32 bytes (all-zero rejected). A key works only for its own purpose. `AuditKeys` refuses the same material for both purposes.
- **`key_id`** = first 32 hex characters of SHA-256(`rig.audit-key-id/v1` NUL purpose NUL key).
- **MAC** = HMAC-SHA-256(K_auth, `rig.audit-mac/v1` NUL key_id NUL canonical(event)). The key id is bound into the MAC.
- **Canonical JSON** is M1's: sorted keys, compact, ASCII-only, no NaN.
- **Verification:** every MAC and digest comparison uses `hmac.compare_digest`. `AuditEnvelope.verify(keyring)` returns `AuthStatus` (`authentic`, `unauthenticated`, `unknown_key`, `mac_mismatch`, `digest_mismatch`, `schema_invalid`) and never raises for bad content.

**What `authentic` means:**
- It proves the event bytes were produced by a holder of `K_auth`.
- HMAC is symmetric: it gives **no non-repudiation** and can't identify which holder.
- It does **not** prove that a tool ran, that a decision was enforced, or that the engine (rather than other code in the same process) produced the record.
- `decision_ref` is an unkeyed digest; checking it proves internal consistency only.
- **Deletion, reordering and truncation of events are not detectable in M2-B.** That needs an ordering chain plus an independent trusted checkpoint (M2-C).

## Key lifecycle limitations

- Keys are held **in process memory only**. M2-B has no key files, environment variables, rotation, ratcheting, escrow or erasure.
- `repr()`/`str()` show only the purpose and `key_id`. Keys can't be pickled, and errors never include material.
- Python can't make memory private: any code in the same process can read key material, for example through `AuditKey._material`. Key compromise and loss handling are M2-C/M2-D design items.

## MemorySink behavior

- **Process memory only.** Every receipt says `durability = "none"`; everything is lost at exit.
- **Validation:** the sink re-validates each envelope's digest. With `verify_keys`, it also verifies the MAC and rejects failures. With `require_authenticated=True`, it rejects envelopes that have no MAC.
- **Rejections, never exceptions, for bad content:** duplicate `event_id`, oversized envelopes (above 17 KiB), and full sinks are all rejected with a reason.
- **Limits:** defaults are 10,000 events and 32 MiB, with hard ceilings of 1,000,000 events and 1 GiB. **The sink never evicts or overwrites.**
- **Order:** acceptance order is preserved, and receipts carry the 0-based `sequence`.
- **Storage:** envelopes are stored as immutable canonical bytes; readers get fresh copies. The sink is thread-safe (one lock).
- **`AuditReceipt`** (`status`, `sequence`, `event_id`, `event_digest`, `auth_status`, `error_code`, `durability`) is returned to the caller and **never stored inside an event**.

## Trust boundaries

| Boundary | Trusted | Untrusted |
|---|---|---|
| Request → builder | M1's parser and digest | The request object (it may be hostile, change between reads, or raise) |
| Record → builder | One detached snapshot whose `decision_digest` recomputes | The record object and its attributes (never read after the snapshot); mismatched or malformed snapshots (rejected); `error_type` (always mapped) |
| Clock / ID factory → builder | Builder code | Their return values and exceptions (closed codes) |
| Builder → sink | Sink code | The envelope (re-checked) |
| Keys | Code that holds them | Everything that only sees events, receipts, `repr()` or errors |

`BaseException` raised by a hostile request object (`KeyboardInterrupt`, `SystemExit`) propagates, as in M1.

### Record snapshot (single read)

The builder reads a record exactly once:

1. It calls `record.to_dict()` one time.
2. It serializes the result to canonical JSON once and parses it back into plain JSON values, which detaches it from any shared or hostile container.
3. It checks the exact field set and recomputes `decision_digest` from that snapshot.

Every engine field of the event comes from this snapshot. **No record attribute is read again**, so an event can't contain engine data that differs from what its `decision_ref` covers. Malformed snapshots give `INVALID_RECORD`. A `decision_digest` that is missing as a string or doesn't recompute gives `RECORD_INCONSISTENT`.

The digest is unkeyed: a match proves internal consistency, not that `PolicyEngine` produced the record.

### Exception boundary

Every call into caller-supplied code (the record, the request, the clock and its time conversion, the ID factory) runs inside an `except Exception` boundary. Failures become closed codes:

| Code | Cause |
|---|---|
| `INVALID_RECORD` / `RECORD_INCONSISTENT` | A malformed or inconsistent record |
| `INVALID_CLOCK` | The clock raised, returned something other than an aware, exact `datetime`, its `tzinfo` misbehaved, or the conversion to UTC failed |
| `INVALID_ID` | The ID factory raised or returned a bad value |
| `BUILD_FAILED` | Anything unexpected |

These errors are raised **outside** the handler, so no attacker-controlled exception is attached as `__cause__` or `__context__`. Messages carry only the code and a fixed field path. `BaseException` still propagates.

### Limitation: the request is parsed twice

`PolicyEngine.evaluate()` parses the caller's request, and the builder parses the same object again, using M1's `coerce_request`, to establish `consistent`.

**What this means for hostile request objects:**
- Their code runs twice: `isinstance` checks may call a hostile `__class__`, and `dict(...)` calls `keys`, `__iter__` and `__getitem__`. Side effects therefore happen twice.
- An object that answers differently the second time gets `mismatch` and no caller fields.
- `Exception` is contained; `BaseException` propagates.

The M1 API is unchanged in M2-B.

**Options for M2-D (not implemented):**
1. **Parse once, pass the typed request (preferred).** The orchestrator parses the mapping once with `parse_request`, passes the typed `AuthorizationRequest` to `evaluate()`, and gives the same typed object to the builder. M1 re-validates typed requests through their own `to_dict()`, so no caller code runs again.
   - Decisions are unchanged for valid input.
   - For input that fails to parse, the orchestrator still has to call `evaluate()` with the original object to get M1's exact reason code, which repeats the hostile-object call on that path only.
2. **Engine-side capture.** A future M1 API returns the parsed request alongside the record. This changes the M1 API and would need separate approval.
3. **Restrict callers to plain JSON data** (`dict`, `list`, `str`, …) at the adapter boundary, so request objects can't run code. This is an adapter (Genesis D) responsibility.

## Known limitations

- **Readable identifiers can be sensitive.**
  - `agent_id`, `tool_id` and `labels` are stored as is.
  - They pass M1's identifier grammar (lowercase ASCII, ≤ 128 characters), which limits their form but not their meaning. Values such as `john.smith-laptop`, `patient-12345` or `mcp://acme-payroll/get-salary` are recorded unchanged.
  - The credential filter is a heuristic and misses short secrets (for example `pw-hunter2`) and token runs shorter than 24 characters.
  - Treat audit events as sensitive data. Pseudonymizing these fields is an open design decision.
- **In-process memory exhaustion.**
  - Code running in the same process can make the builder do unbounded work, for example a hostile `to_dict()` that returns very large structures, since no size cap is applied before serialization.
  - `MemorySink` is bounded (by default 10,000 events and 32 MiB), but its contents live in process memory.
  - Neither component defends against an attacker who already runs code in the process.
- **The request is parsed twice:** see the previous section. Hostile request objects run their code once in `evaluate()` and once in the builder.
- **No persistent storage.** Everything is lost when the process exits, and receipts always say `durability: "none"`. Ordering chains, checkpoints and on-disk verification are M2-C.
- **No runtime enforcement.**
  - Events record decisions only; `enforced` is always `false`.
  - Nothing here blocks, delays or approves a tool call, and nothing proves that a tool ran or didn't run.
  - Enforcement adapters are Genesis D.
- **HMAC limits.**
  - An `authentic` envelope proves only that a holder of `K_auth` sealed it.
  - HMAC is symmetric: there is no non-repudiation, and any holder can forge.
  - It doesn't prove that `PolicyEngine` produced the decision: `decision_ref` is an unkeyed consistency digest, and any in-process code can create a self-consistent record.
  - Deleting, reordering or replaying whole envelopes can't be detected without an ordering chain and an independent checkpoint (M2-C).
- **Keys live in process memory**, readable by code in the same process, with no rotation or erasure.
- **`BUILD_FAILED` hides the cause of unexpected internal errors.** It keeps attacker-controlled exceptions out of diagnostics, but genuine bugs then surface only as that code.

## Remaining work

**M2-C:**
- JSONL persistence;
- the ordering chain (`seq`, `prev_event_digest`, segment headers);
- external checkpoints;
- an on-disk verifier;
- key provisioning from files;
- rotation and key-loss handling;
- quotas and degradation signals;
- file-safety controls.

**M2-D:**
- an evaluator that runs evaluation and auditing in one step;
- `BEST_EFFORT` and `AUDIT_REQUIRED` failure semantics;
- the full failure matrix;
- an independent audit.

**Out of scope for Genesis B:** runtime enforcement, authenticated caller identity, and provenance that can be proven outside the process (Genesis D).
