# Audit Foundation (Genesis B2-M2-B, B2-P1 privacy hardening, B2-P2 projection)

> **Status: development, unreleased.** M2-B is the pure, in-memory foundation of the audit
> subsystem. B2-P1 (merged into `main`) adds an opt-in privacy-hardened event schema
> (`rig.audit-event/v3`). B2-P2 (a development branch, **not merged**) adds the privacy-safe
> audit projection (`rig.audit-projection/v1`), the persistence gate for projections and
> optional fidelity verification (see
> [Privacy-safe audit projection](#privacy-safe-audit-projection-b2-p2)). It is
> **not** a complete or production audit log:
> - there is no persistence, cross-event ordering chain, checkpointing, key storage or rotation (M2-C);
> - nothing yet evaluates and audits in one step, and there are no failure modes (M2-D).
>
> The API and schema may change.

`rig_sentinel.audit` builds privacy-minimized, versioned **audit events** from M1 policy
decisions, optionally authenticates them, and can keep them in process memory. Events record
**decisions**. They never claim that a tool ran, that a decision was enforced
(`"enforced": false` always), or that an event was saved.

## Architecture

```text
caller ──▶ PolicyEngine.evaluate(request) ──▶ DecisionRecord          (M1, unchanged)
   │                                               │
   └── same request object ──▶ AuditEventBuilder ◀─┘
                                 │  re-parse request with M1's parser; compare request_digest
                                 │  redaction: kind/depth + HMAC refs (K_ref) or nothing
                                 ▼
                              AuditEvent (frozen, closed schema, validated on construction)
                                 │  AuditEnvelope.seal(event, K_auth | None)
                                 ▼
                              AuditEnvelope ──▶ MemorySink.append() ──▶ AuditReceipt
```

| Module | Responsibility |
|---|---|
| `events.py` | Frozen models, the `rig.audit-event/v2` and `rig.audit-event/v3` events, the `rig.audit-envelope/v1` envelope, and envelope sealing and verification |
| `builder.py` | `AuditEventBuilder`: `DecisionRecord` + original request → event or envelope (v2 by default, v3 when selected) |
| `redaction.py` | Resource minimization, keyed references, credential-like identifier filter, `error_type` mapping, and the v3 source check `check_persistable` (alias `check_v3_projection_source`) |
| `projection.py` | B2-P2: projection schema, projector, `check_projection_persistable` gate, `verify_projection_fidelity` |
| `validation.py` | Field checks and closed-schema parsers for untrusted dictionaries (`event_from_dict` for v2, `event_v3_from_dict` for v3) |
| `chain.py` | Canonical digests, HMAC-SHA-256, pseudonyms, constant-time comparison, `AuthStatus` |
| `keys.py` | `AuditKey` and `AuditKeys`: in-memory keys with purpose binding |
| `sinks.py` | `AuditSink` protocol, `MemorySink`, `AuditReceipt` |
| `errors.py` | `AuditError` and closed `AuditErrorCode` values |

**Dependencies:**
- `rig_sentinel.audit` depends on `rig_sentinel.policy`, and `rig_sentinel.policy` never imports `rig_sentinel.audit`.
- The package uses the standard library only (`hmac`, `hashlib`, `secrets`, `json`, `threading` in `sinks.py`), with no file, database or network I/O.
- `tests/test_audit_isolation.py` checks all of this.

Envelope sealing and verification live in `events.py`, next to the envelope model; `chain.py` holds only the primitives. This avoids an import cycle.

## Event schema

One envelope:

```json
{"envelope_schema": "rig.audit-envelope/v1",
 "event": { "schema_version": "rig.audit-event/v2", "audit": {}, "engine": {}, "caller": {} },
 "event_digest": "<64 hex: SHA-256('rig.audit-event/v2' NUL canonical(event))>",
 "auth": {"algorithm": "HMAC-SHA256", "key_id": "<32 hex>", "mac": "<64 hex>"} | null}
```

Every object has a closed field set: unknown or missing fields are rejected, and absent values are explicit `null`.

### Fields by provenance

| Section | Fields | Source |
|---|---|---|
| `audit` | `event_id`, `correlation_id` (128-bit random hex), `recorded_at` (UTC, µs), `redaction_mode` (`scoped` or `no-ref-key`), `ref_key_id` | Generated by the audit layer |
| `engine` | `decision`, `reason_code`, `decision_ref` (= the record's `decision_digest`), `protected`, `enforced` (must be `false`), `record_schema`, `engine_version`, `evaluated_at`, `policy_id`, `policy_version`, `policy_sha256`, `deciding_rule_ids`/`_count`, `matched_rule_ids`/`_count` (first 32 + total), `approval`, `error_class`, `request_digest` | One detached snapshot of the M1 `DecisionRecord` (see below), accepted only if its `decision_digest` recomputes from that snapshot |
| `caller` | `consistency`, `agent_id`, `assurance_claim`, `tool_id`, `manifest_sha256`, `operation`, `environment`, `labels`, `resource` {`kind`, `depth`, `authority_ref`, `resource_ref`}, `session_ref`, `request_ref`, `redacted_fields` | **Claims made by the caller.** Not authenticated by anyone |

**`caller.consistency`:**
- `consistent`: the request object passed to the builder re-parses (with M1's own parser) to the record's `request_digest`. This proves the recorded fields are the ones that were evaluated. It does **not** prove who the caller is, so the value is never called "verified".
- `invalid_request`: the request doesn't parse.
- `mismatch`: it parses to a different digest (changed after evaluation, or a hostile object).
- `not_applicable`: the record has no `request_digest`, for example policy unavailable.

In every state except `consistent`, all caller fields are `null`.

**Never recorded:**
- raw requests, tool arguments, prompts, credentials, Authorization headers;
- exception messages, untrusted exception class names;
- raw session or request ids;
- persistence status.

## Privacy defaults

| Data | `scoped` (K_ref present) | `no-ref-key` (no K_ref) |
|---|---|---|
| Resource | `kind`, `depth`, `authority_ref` = HMAC(K_ref, authority), `resource_ref` = HMAC(K_ref, canonical resource) | `kind` and `depth` only; no authority, no reference |
| `session_id` / `request_id` | `session_ref` / `request_ref` = HMAC(K_ref, id) | Omitted |
| `agent_id`, `tool_id`, `labels` | Stored as is (policy vocabulary), unless they look like credentials | Same |

- **Pseudonyms** are HMAC-SHA-256 under `K_ref`, cut to 128 bits, with a separate namespace per kind (`rig.audit-ref/v1/session`, `…/resource/db`, …). **Unkeyed SHA-256 is never used as a pseudonym**: guessable values such as paths, tables and hosts could be brute-forced from it.
- **No full-identifier mode** exists in M2-B.
- **Credential-like identifiers** (known prefixes such as `sk-`, `xoxb-`, `glpat-`, or long mixed letter-digit runs) are dropped and counted in `redacted_fields`. This is a heuristic and only a second line of defense.
- **`redacted_fields` is an exact count**, never saturated. At most 1 (`agent_id`) + 1 (`tool_id`) + 32 unique labels (M1's `MAX_REQUEST_LABELS`; `parse_request` rejects more) = 34 redactions are reachable, below the schema bound of 64. A test fails if M1's label limit ever grows past that bound.
- **`error_class`** is a built-in exception name, `UnlistedError` or `InternalError`. Anything else maps to `UnlistedError`.

## Schema v3 (B2-P1 privacy hardening)

`rig.audit-event/v2` stays the **default** and is unchanged. Version 3 is used only when it is
selected explicitly:

```python
builder = AuditEventBuilder(keys, event_schema=AUDIT_EVENT_SCHEMA_V3)
```

Any other value of `event_schema` (including a `str` subclass, a different case or extra
whitespace) is rejected with `UNSUPPORTED_SCHEMA`. A v2 event is never reinterpreted as v3:
`event_from_dict` accepts only v2, `event_v3_from_dict` accepts only v3, and
`envelope_from_dict` chooses the parser from the exact `schema_version` string. A v2 event
relabelled as v3, or a v3 event relabelled as v2, fails closed-schema validation, and in an
envelope it also breaks the digest and MAC, because `schema_version` is part of the
authenticated content.

### v3 caller section

The `audit` and `engine` sections are the same as in v2. The `caller` section is replaced by a
closed set of fields in which **actor and tool identities are never stored in plain text**:

| Field | `pseudonymized` (K_ref present) | `omitted` (no K_ref) |
|---|---|---|
| `identity_mode` | `pseudonymized` | `omitted` |
| `agent_ref` | HMAC(K_ref, `rig.audit-ref/v1/agent` NUL agent_id)[:128 bits] | `null` |
| `tool_ref` | HMAC(K_ref, `rig.audit-ref/v1/tool` NUL tool_id)[:128 bits] | `null` |
| `readable_labels` | Labels from the approved allowlist, sorted | Same |
| `label_refs` | Sorted, unique HMAC(K_ref, `rig.audit-ref/v1/label` NUL label) of every **other** label | `null` (other labels are dropped and counted) |
| `omitted_labels_count` | `null` (nothing is omitted: other labels become `label_refs`) | Exact number of labels dropped because no K_ref was available; `0`, never absent, when none were |
| `manifest_ref` | HMAC(K_ref, `rig.audit-ref/v1/manifest` NUL manifest_sha256)[:128 bits], or `null` if the request has no manifest digest | `null` |
| `resource` | `kind`, `depth`, keyed `authority_ref` and `resource_ref` (as in v2) | `kind` and `depth` only |
| `session_ref`, `request_ref` | Keyed references (as in v2) | `null` |
| `assurance_claim`, `operation`, `environment` | Closed enumerations, readable | Same |
| `consistency` | As in v2 | As in v2 |

There is no `agent_id`, `tool_id`, `manifest_sha256`, `labels` or `redacted_fields` field in
v3, and no plain-text fallback: when K_ref is missing, identities are omitted, not written in
clear.

**Tool manifest digest (security review finding H-1).** The caller-supplied `manifest_sha256`
identifies the tool to anyone who knows its manifest, which would undo `tool_ref`. v3 therefore
never copies it into an event: with K_ref it becomes `manifest_ref` in its own namespace
(`manifest`, separate from `tool`); without K_ref it is dropped. The raw digest is not used as
a pseudonym, and no unkeyed hash of it is recorded in the caller section. v2 still records
`manifest_sha256` unchanged, and M1 still uses it for decisions and in `request_digest`.

**Omitted-label accounting (security review finding M-1).** In `omitted` mode,
`omitted_labels_count` is the number of the request's labels that were not readable (outside
the approved allowlist, or outside a narrower operator allowlist) and could not be referenced
because K_ref is absent. Labels are counted once each (M1 de-duplicates them). The count:
- is an exact `int` (booleans, `int` subclasses, floats and strings are rejected), from 0 up to `MAX_REQUEST_LABELS` (32) minus the number of readable labels;
- is `0` when nothing was omitted, and is never absent in `omitted` mode;
- is `null` in `pseudonymized` mode, and whenever the request is not `consistent`.

Labels rejected by request validation are a different case: a request with more than 32 labels
fails M1's parser, so the event has `consistency = "invalid_request"`, every caller claim is
`null`, and nothing is counted. The counter is separate from v2's `redacted_fields`; there is no
invariant connecting them.

**Validation rules** (enforced on construction and when parsing):
- `identity_mode` is `pseudonymized` exactly when `audit.redaction_mode` is `scoped` (K_ref present, `ref_key_id` set), and `omitted` exactly when it is `no-ref-key`.
- In `pseudonymized` mode, `agent_ref`, `tool_ref` and `label_refs` are required, `manifest_ref` is optional, and `omitted_labels_count` must be `null`. In `omitted` mode, `agent_ref`, `tool_ref`, `label_refs`, `manifest_ref`, `session_ref` and `request_ref` must be `null`, and `omitted_labels_count` is required. A `no-ref-key` event may contain no keyed reference at all.
- References are exactly 32 lowercase hexadecimal characters; `label_refs` is sorted, unique and holds at most 32 entries.
- Readable labels plus `label_refs` (pseudonymized), or readable labels plus `omitted_labels_count` (omitted), may not exceed `MAX_REQUEST_LABELS` (`LIMIT_EXCEEDED`).
- When `consistency` is not `consistent`, every caller claim, including `manifest_ref` and `omitted_labels_count`, is `null`, as in v2.
- `readable_labels` must be a subset of the approved allowlist.

**Domain separation:** agent, tool, manifest and label references use separate namespaces under
the existing `rig.audit-ref/v1/<kind>` construction, so the same string used as an agent, a
tool, a manifest digest and a label produces four unrelated references. **No unkeyed hash is
ever used as a caller identifier**, and K_ref is never written into an event, error or `repr()`.

### Readable label allowlist

`APPROVED_READABLE_LABELS = {"reviewed", "untrusted_content_present"}`, taken from the labels
the M1 documentation and fixtures already use. Labels are compared as exact ASCII strings:
look-alike Unicode, zero-width characters, percent-encoding, Base64 and different case never
match. There is **no free-text exception**.

A deployment can narrow the set (`readable_labels=frozenset({"reviewed"})`, or `frozenset()`
for none) but never extend it: any label outside the approved set, a `str` subclass, or a
container that is not a `set` or `frozenset` is rejected with `INVALID_FIELD`, without echoing
the value. `readable_labels=None` means the full approved set. Labels that are not readable
become `label_refs` in `pseudonymized` mode and are dropped and counted in
`omitted_labels_count` in `omitted` mode.

### v3 source check (`check_persistable`)

> **Superseded for persistence by B2-P2.** v3 events still contain M1's unkeyed request,
> decision and approval-binding digests, so a v3 envelope must **not** be persisted. Its
> behaviour is unchanged, and `check_v3_projection_source` is the preferred alias, but it is
> now a *precondition for projection*. Only `check_projection_persistable` (B2-P2) authorizes
> persistence, and only for projection envelopes.

`check_persistable(envelope, keys, *, readable_labels=None) -> PersistenceVerdict` was introduced
in P1 as the check for a future persistent sink. It is **not** a sink and stores nothing. It
accepts an envelope only if all of the following hold:

1. it is an `AuditEnvelope` (exact type) whose event is v3. v2 events are refused with `v2_event_not_persistable`;
2. its digest and MAC verify under `keys`. There is no unauthenticated mode and no option to skip or downgrade verification: unsealed envelopes, unknown keys, bad MACs and bad digests are refused with their own codes;
3. its canonical bytes re-parse under the closed v3 schema to identical bytes. This refuses events altered in memory behind the model's back, even when a holder of K_auth sealed them afterwards (`schema_invalid`);
4. every readable label is within `readable_labels` (default and maximum: the approved set). Otherwise the result is `label_not_allowed`.

The gate is pure: it never modifies, repairs or re-seals the envelope, performs no I/O, and
returns a verdict instead of raising for invalid content. The verdict carries a closed
`PersistenceCode` only, never event content. Passing it proves that the event follows the v3
privacy rules and was sealed by a holder of K_auth. It does **not** prove that `PolicyEngine`
made the decision, that anything was stored, or that a tool ran.

`MemorySink` accepts both v2 and v3 envelopes, unchanged; it is in-memory only and does not
call the gate.

### Digest and MAC domain for v3 (compatibility note)

v3 envelopes reuse the M2-B envelope contract unchanged: the event digest is
SHA-256(`rig.audit-event/v2` NUL canonical(event)) and the MAC is
HMAC-SHA-256(K_auth, `rig.audit-mac/v1` NUL key_id NUL canonical(event)), for both event
versions. The digest domain string therefore still says `v2` for v3 events. This is a
**temporary compatibility decision for P1**, accepted by the independent security review: the
event's own `schema_version` is inside the digested and authenticated bytes, so a v2 and a v3
event can never share a digest or MAC, and relabelling a sealed event as the other version
fails verification and parsing (tests in `tests/test_audit_p1_remediation.py`). P1 introduces
no new envelope schema. Version-specific envelope domains are **future M2-C design work** and
need their own review.

### What v3 does not provide

- **Pseudonymization is not anonymity.** References are stable for a given K_ref, so all events of one agent, tool, manifest, label, session or resource can be linked to each other. Anyone who holds K_ref can confirm a guessed identifier by recomputing its reference, and so can test a list of candidate names.
- **Readable fields still carry information.** Assurance, operation, environment, resource kind and depth, timestamps, policy and rule ids, the approved labels and `omitted_labels_count` stay readable; together they can make events correlatable or identifiable.
- **The engine section keeps M1's unkeyed digests.** `engine.request_digest` (and `decision_ref`, which covers it) are unkeyed SHA-256 digests of the full canonical request, including agent id, tool id, manifest digest, labels, resource and any session or request id. Someone who can guess *every* field of a request can confirm the guess against them. Random session or request ids make this impractical, but requests without them may have a small guessing space. These digests are kept unchanged because M1's decision and request-digest semantics must not change. B2-P2 removes them from everything intended for persistence (see [Privacy-safe audit projection](#privacy-safe-audit-projection-b2-p2)).
- **The approval block carries an unkeyed request binding and readable approver ids.** On `REQUIRE_APPROVAL` decisions, `engine.approval.request_binding_sha256` is M1's unkeyed SHA-256 over agent id, tool id, operation, resource, environment, session id and `policy_sha256`. In a v3 event, operation, environment and `policy_sha256` are readable, so this is an *easier* guess-confirmation target than `request_digest`. `engine.approval.eligible_approvers` holds up to 32 policy approver ids in clear, and those ids can name people. Both are removed or keyed by B2-P2 projections.
- **Forged but well-formed content.** The schema can't tell a genuine reference from any other 32-hex string, or a genuine count from any other in-range count. Only the MAC protects these, so any holder of K_auth can seal well-formed but false values.
- **K_ref epochs.** A new K_ref produces unrelated references, so events from different keys can't be correlated by reference. There is no rotation or epoch management yet (M2-C).
- **Omitted mode loses information.** Without K_ref, identities, the manifest digest, non-approved labels (only their number is kept) and session and request ids are not recorded.
- **No storage and no enforcement.** P1 adds no persistence (JSONL is M2-C), and events still record decisions only; nothing blocks a tool call at runtime.

**How B2-P2 limits these residuals:** v3 events and their unkeyed digests stay in memory. The
representation intended for persistence is the separately authenticated projection (its own
envelope schema, digest and MAC domains), in which M1's unkeyed request digest, decision digest
and approval request binding are replaced by keyed references, raw approver ids by keyed
references, and the v3 event digest and MAC are dropped. The persistence gate refuses every v1
envelope (v2 and v3 events). The residuals still apply to any v3 event kept in memory, logged or
exported by other means.

## Privacy-safe audit projection (B2-P2)

A **projection** is the only representation intended for persistent storage. It is derived from
an already sealed v3 envelope, and no v2 or v3 envelope may be persisted.

```text
DecisionRecord + request ─▶ AuditEventBuilder(v3) ─▶ AuditEnvelope v1 {v3}  (in memory)
        project(envelope, keys, profile=KEYED | UNLINKED)
          1. exact types; closed re-parse to identical bytes; digest + MAC under K_auth
          2. profile pairing read from the re-parsed bytes: KEYED <-> exactly scoped,
             UNLINKED <-> exactly no-ref-key (explicit opt-in only; never a fallback)
          3. keyed references; raw digests, approver ids, v3 event_digest and MAC dropped
          4. seal as rig.audit-envelope/v2 { rig.audit-projection/v1 } with K_auth
        check_projection_persistable(projection_envelope, keyring, ...) ─▶ ValidatedProjection
        (a future M2-C sink writes ValidatedProjection.canonical; not implemented)
```

### What changes in the engine section

| v3 field | Projection |
|---|---|
| `request_digest` (unkeyed) | `request_ref` = HMAC(K_eref, `rig.audit-engine-ref/v1/request-digest` NUL digest)[:128 bits] |
| `decision_ref` (unkeyed M1 `decision_digest`) | `decision_ref_keyed` (domain `.../decision-digest`) |
| `approval.request_binding_sha256` (unkeyed) | `approval.binding_ref` (domain `.../approval-binding`) |
| `approval.eligible_approvers` (raw ids) | `approval.eligible_approver_refs`: HMAC(K_ref, `rig.audit-ref/v1/approver` NUL id) of v3's retained ids, sorted by reference value |
| — | `engine_ref_key_id`: the K_eref key id (key epoch) |

- **Engine-reference key.** K_eref = HMAC-SHA-256(K_ref, `rig.audit-key-derive/v1` NUL `engine-ref`), key purpose `ENGINE_REF`. It can't be built from raw bytes and can't be used for P1 identity references or MACs. Derivation gives purpose and domain separation, **not** independent compromise: whoever holds K_ref can derive K_eref.
- **Approvers.** v3 keeps the first `min(count, 32)` approver ids in sorted raw order. The projection keys exactly those ids (it never sees the others), sorts the references, and keeps the total count (0 to 100, M1's limit). `count > len(refs)` shows truncation.
- **Request references** follow the v3 rule: required for `consistent`, forbidden for `not_applicable`, and present for `mismatch` and `invalid_request` only when the source had a request digest.
- **Unlinked profile.** Only by explicit `ProjectionProfile.UNLINKED`, and only for sources whose redaction mode is exactly `no-ref-key`. All engine and approver references are `null` and only the approver count is kept. Such a projection can never be tied to an M1 record.
- **Envelope.** The projection is sealed in `rig.audit-envelope/v2` with its own domains: digest SHA-256(`rig.audit-projection/v1` NUL canonical) and MAC HMAC-SHA-256(K_auth, `rig.audit-projection-mac/v1` NUL key_id NUL canonical). The MAC is mandatory. Verification needs only K_auth and accepts only an exact `dict` keyring.

### Persistence gate (`check_projection_persistable`)

`check_projection_persistable(envelope, keys, *, readable_labels=None, expected_epoch=None) -> ProjectionGateResult`
is pure: it performs no I/O, never modifies the envelope and never raises for content
(`BaseException` propagates). It accepts only if all of the following hold, in this order:

1. `keys` is an exact `dict` mapping each K_auth key id to its AUTH key (`keyring_invalid`); `readable_labels` and `expected_epoch` are valid (`configuration_invalid`).
2. The envelope is exactly a `ProjectionEnvelope`. v1 envelopes are refused by event version (`v3_event_not_persistable`, `v2_event_not_persistable`); anything else (dicts, mappings, look-alikes, subclasses) is `not_a_projection`.
3. Its canonical bytes re-parse under the closed envelope v2 and projection v1 schemas to identical bytes (`schema_invalid`).
4. A deep scan of the parsed bytes finds no forbidden key at any depth (`request_digest`, `decision_ref`, `decision_digest`, `request_binding_sha256`, `eligible_approvers`, `event_digest`, `source_ref`, `agent_id`, `tool_id`, `manifest_sha256`, `labels`, `redacted_fields`) and no 64-hex string outside `projection.engine.policy_sha256`, `projection_digest` and `auth.mac` (`forbidden_field`). This also refuses a 64-hex value placed in a readable identifier such as a rule id or `policy_id`.
5. Digest and MAC verify under K_auth (`digest_mismatch`, `unknown_key`, `authentication_failed`).
6. When `expected_epoch` is given (`ProjectionEpoch.keyed(K_ref)` or `ProjectionEpoch.unlinked()`), the projection's profile, `ref_key_id` and `engine_ref_key_id` equal it (`epoch_mismatch`).
7. Readable labels are within the allowlist (`label_not_allowed`).

On success, the result carries a `ValidatedProjection`: the exact canonical bytes that were
checked, plus the projection digest, K_auth key id, event id, profile and epoch key ids. Only the
gate can issue one. A passed gate writes nothing and does **not** authorize writing through any
sink that doesn't apply the gate itself. The result carries codes, never event values.

### Fidelity verification (`verify_projection_fidelity`)

`verify_projection_fidelity(envelope, record, keys) -> FidelityResult` returns exactly `MATCH`,
`MISMATCH` or `NOT_VERIFIABLE`. **Integrity** (the MAC under K_auth) and **fidelity**
(agreement with an original M1 `DecisionRecord`) are separate questions: integrity is a
precondition, never the result.

| Result | When |
|---|---|
| `NOT_VERIFIABLE` | The projection isn't an exact, authentic `ProjectionEnvelope` under `keys.auth`; it is `unlinked`; `keys` lacks K_ref or K_auth; K_ref isn't the projection's epoch (`ref_key_id`); or the record is missing, not an exact `DecisionRecord`, not self-consistent, or not one the audit builder accepts |
| `MISMATCH` | Authentic and verifiable, but some engine field, keyed reference, the K_eref epoch, the approver references or count, or the approval binding differs from what the record yields |
| `MATCH` | Every engine-section value matches the record |

The record is read once into a detached, digest-checked snapshot, exactly as the builder does.
Approvers are compared by sorting the raw ids, taking the first `min(count, 32)`, keying each
with K_ref, sorting the references, and comparing them and the count. `MATCH` means only "this
projection is consistent with this self-consistent record under this K_ref epoch". It does
**not** prove that `PolicyEngine` produced the record (the record's digest is unkeyed), that a
tool ran or was blocked, or anything about the caller section, which isn't compared. Because it
needs K_ref, the function is itself a guess-confirmation tool for whoever calls it.

### Exception behaviour

- Projection parsers raise value-free `AuditError` objects with no chained context.
- `project`, the gate and fidelity verification contain `Exception` subclasses raised by hostile in-memory objects: the projector converts them to a closed `AuditError` raised outside the handler, the gate returns a refusal code, and fidelity returns `NOT_VERIFIABLE`.
- `BaseException` subclasses that are not `Exception` (`KeyboardInterrupt`, `SystemExit`, `GeneratorExit`, custom ones) are never caught, converted or reconstructed; they propagate unchanged.
- Traceback frames of these calls hold the inputs the caller supplied. Don't ship exceptions with frame locals to external systems.
- The M2-B v2/v3 parsers are unchanged. Their enum errors keep the original `ValueError`, which quotes the offending input value, in `__context__` (hidden from default tracebacks). A separate M2-B patch has been proposed.

### What projections do not provide

- **Not anonymity.** References are stable within a K_ref epoch. Identical requests share `request_ref`, identical approvers share references, and any K_ref holder can confirm guesses.
- **Readable quasi-identifiers remain:** timestamps, decision, reason code, rule ids, policy id and version, `policy_sha256` (which can tell known policies apart), counts and approved labels.
- **Forged but well-formed content.** Any K_auth holder can seal a well-formed projection with false references or counts. Only fidelity verification against an original record (with K_ref) can detect that.
- **K_ref compromise** exposes every reference of that epoch to guess confirmation. Persisted records can't be re-keyed in place.
- **64-hex identifier limitation.** The gate refuses any 64-character hexadecimal string outside `policy_sha256`, the projection digest and the MAC, including inside readable identifiers such as rule ids and `policy_id`, because such a value could be a smuggled unkeyed digest. A policy whose rule or policy id is a 64-character hex string therefore can't be persisted (fail closed, a possible false positive). Give such identifiers non-hex names.
- **Fidelity `MATCH` covers the engine section only.** It doesn't compare the caller section (which would need the original request), and it doesn't prove `PolicyEngine` provenance.
- **No persistence implemented yet.** The gate and `ValidatedProjection` are pure; nothing writes them anywhere. A persistent sink, ordering chain, checkpoints and key management are M2-C.
- **No runtime enforcement.** Projections record decisions only (`enforced` is always `false`); nothing blocks, delays or approves a tool call (Genesis D).

## HMAC design and limitations

- **Two independent keys:**
  - `K_ref` (purpose `ref`) for pseudonyms;
  - `K_auth` (purpose `auth`) for envelopes.

  Both are 32 bytes from `secrets.token_bytes`, or supplied as exactly 32 bytes (all-zero rejected). A key works only for its own purpose. `AuditKeys` refuses the same material for both purposes.
- **`key_id`** = first 32 hex characters of SHA-256(`rig.audit-key-id/v1` NUL purpose NUL key).
- **MAC** = HMAC-SHA-256(K_auth, `rig.audit-mac/v1` NUL key_id NUL canonical(event)). The key id is bound into the MAC.
- **Canonical JSON** is M1's: sorted keys, compact, ASCII-only, no NaN.
- **Verification:** every MAC and digest comparison uses `hmac.compare_digest`. `AuditEnvelope.verify(keyring)` returns `AuthStatus` (`authentic`, `unauthenticated`, `unknown_key`, `mac_mismatch`, `digest_mismatch`, `schema_invalid`) and never raises for bad content.

**What `authentic` means:**
- It proves the event bytes were produced by a holder of `K_auth`.
- HMAC is symmetric: it gives **no non-repudiation** and can't identify which holder.
- It does **not** prove that a tool ran, that a decision was enforced, or that the engine (rather than other code in the same process) produced the record.
- `decision_ref` is an unkeyed digest; checking it proves internal consistency only.
- **Deletion, reordering and truncation of events are not detectable in M2-B.** That needs an ordering chain plus an independent trusted checkpoint (M2-C).

## Key lifecycle limitations

- Keys are held **in process memory only**. M2-B has no key files, environment variables, rotation, ratcheting, escrow or erasure.
- `repr()`/`str()` show only the purpose and `key_id`. Keys can't be pickled, and errors never include material.
- Python can't make memory private: any code in the same process can read key material, for example through `AuditKey._material`. Key compromise and loss handling are M2-C/M2-D design items.

## MemorySink behavior

- **Process memory only.** Every receipt says `durability = "none"`; everything is lost at exit.
- **Validation:** the sink re-validates each envelope's digest. With `verify_keys`, it also verifies the MAC and rejects failures. With `require_authenticated=True`, it rejects envelopes that have no MAC.
- **Rejections, never exceptions, for bad content:** duplicate `event_id`, oversized envelopes (above 17 KiB), and full sinks are all rejected with a reason.
- **Limits:** defaults are 10,000 events and 32 MiB, with hard ceilings of 1,000,000 events and 1 GiB. **The sink never evicts or overwrites.**
- **Order:** acceptance order is preserved, and receipts carry the 0-based `sequence`.
- **Storage:** envelopes are stored as immutable canonical bytes; readers get fresh copies. The sink is thread-safe (one lock).
- **`AuditReceipt`** (`status`, `sequence`, `event_id`, `event_digest`, `auth_status`, `error_code`, `durability`) is returned to the caller and **never stored inside an event**.

## Trust boundaries

| Boundary | Trusted | Untrusted |
|---|---|---|
| Request → builder | M1's parser and digest | The request object (it may be hostile, change between reads, or raise) |
| Record → builder | One detached snapshot whose `decision_digest` recomputes | The record object and its attributes (never read after the snapshot); mismatched or malformed snapshots (rejected); `error_type` (always mapped) |
| Clock / ID factory → builder | Builder code | Their return values and exceptions (closed codes) |
| Builder → sink | Sink code | The envelope (re-checked) |
| Keys | Code that holds them | Everything that only sees events, receipts, `repr()` or errors |

`BaseException` raised by a hostile request object (`KeyboardInterrupt`, `SystemExit`) propagates, as in M1.

### Record snapshot (single read)

The builder reads a record exactly once:

1. It calls `record.to_dict()` one time.
2. It serializes the result to canonical JSON once and parses it back into plain JSON values, which detaches it from any shared or hostile container.
3. It checks the exact field set and recomputes `decision_digest` from that snapshot.

Every engine field of the event comes from this snapshot. **No record attribute is read again**, so an event can't contain engine data that differs from what its `decision_ref` covers. Malformed snapshots give `INVALID_RECORD`. A `decision_digest` that is missing as a string or doesn't recompute gives `RECORD_INCONSISTENT`.

The digest is unkeyed: a match proves internal consistency, not that `PolicyEngine` produced the record.

### Exception boundary

Every call into caller-supplied code (the record, the request, the clock and its time conversion, the ID factory) runs inside an `except Exception` boundary. Failures become closed codes:

| Code | Cause |
|---|---|
| `INVALID_RECORD` / `RECORD_INCONSISTENT` | A malformed or inconsistent record |
| `INVALID_CLOCK` | The clock raised, returned something other than an aware, exact `datetime`, its `tzinfo` misbehaved, or the conversion to UTC failed |
| `INVALID_ID` | The ID factory raised or returned a bad value |
| `BUILD_FAILED` | Anything unexpected |

These errors are raised **outside** the handler, so no attacker-controlled exception is attached as `__cause__` or `__context__`. Messages carry only the code and a fixed field path. `BaseException` still propagates.

### Limitation: the request is parsed twice

`PolicyEngine.evaluate()` parses the caller's request, and the builder parses the same object again, using M1's `coerce_request`, to establish `consistent`.

**What this means for hostile request objects:**
- Their code runs twice: `isinstance` checks may call a hostile `__class__`, and `dict(...)` calls `keys`, `__iter__` and `__getitem__`. Side effects therefore happen twice.
- An object that answers differently the second time gets `mismatch` and no caller fields.
- `Exception` is contained; `BaseException` propagates.

The M1 API is unchanged in M2-B.

**Options for M2-D (not implemented):**
1. **Parse once, pass the typed request (preferred).** The orchestrator parses the mapping once with `parse_request`, passes the typed `AuthorizationRequest` to `evaluate()`, and gives the same typed object to the builder. M1 re-validates typed requests through their own `to_dict()`, so no caller code runs again.
   - Decisions are unchanged for valid input.
   - For input that fails to parse, the orchestrator still has to call `evaluate()` with the original object to get M1's exact reason code, which repeats the hostile-object call on that path only.
2. **Engine-side capture.** A future M1 API returns the parsed request alongside the record. This changes the M1 API and would need separate approval.
3. **Restrict callers to plain JSON data** (`dict`, `list`, `str`, …) at the adapter boundary, so request objects can't run code. This is an adapter (Genesis D) responsibility.

## Known limitations

- **Readable identifiers can be sensitive (v2).**
  - In v2 events (the default), `agent_id`, `tool_id` and `labels` are stored as is. v3 events replace them with keyed references or omit them (see [Schema v3](#schema-v3-b2-p1-privacy-hardening)), and `check_persistable` refuses v2 events.
  - They pass M1's identifier grammar (lowercase ASCII, ≤ 128 characters), which limits their form but not their meaning. Values such as `john.smith-laptop`, `patient-12345` or `mcp://acme-payroll/get-salary` are recorded unchanged.
  - The credential filter is a heuristic and misses short secrets (for example `pw-hunter2`) and token runs shorter than 24 characters.
  - Treat audit events as sensitive data, in v2 and v3 alike.
- **In-process memory exhaustion.**
  - Code running in the same process can make the builder do unbounded work, for example a hostile `to_dict()` that returns very large structures, since no size cap is applied before serialization.
  - `MemorySink` is bounded (by default 10,000 events and 32 MiB), but its contents live in process memory.
  - Neither component defends against an attacker who already runs code in the process.
- **The request is parsed twice:** see the previous section. Hostile request objects run their code once in `evaluate()` and once in the builder.
- **No persistent storage.** Everything is lost when the process exits, and receipts always say `durability: "none"`. Ordering chains, checkpoints and on-disk verification are M2-C.
- **No runtime enforcement.**
  - Events record decisions only; `enforced` is always `false`.
  - Nothing here blocks, delays or approves a tool call, and nothing proves that a tool ran or didn't run.
  - Enforcement adapters are Genesis D.
- **HMAC limits.**
  - An `authentic` envelope proves only that a holder of `K_auth` sealed it.
  - HMAC is symmetric: there is no non-repudiation, and any holder can forge.
  - It doesn't prove that `PolicyEngine` produced the decision: `decision_ref` is an unkeyed consistency digest, and any in-process code can create a self-consistent record.
  - Deleting, reordering or replaying whole envelopes can't be detected without an ordering chain and an independent checkpoint (M2-C).
- **Keys live in process memory**, readable by code in the same process, with no rotation or erasure.
- **`BUILD_FAILED` hides the cause of unexpected internal errors.** It keeps attacker-controlled exceptions out of diagnostics, but genuine bugs then surface only as that code.

## Remaining work

**M2-C:**
- JSONL persistence that accepts only `ProjectionEnvelope` objects, applies `check_projection_persistable` before writing, and writes `ValidatedProjection.canonical` unchanged;
- the ordering chain (`seq`, `prev_event_digest`, segment headers);
- external checkpoints;
- an on-disk verifier;
- key provisioning from files;
- rotation and key-loss handling;
- quotas and degradation signals;
- file-safety controls.

**M2-D:**
- an evaluator that runs evaluation and auditing in one step;
- `BEST_EFFORT` and `AUDIT_REQUIRED` failure semantics;
- the full failure matrix;
- an independent audit.

**Out of scope for Genesis B:** runtime enforcement, authenticated caller identity, and provenance that can be proven outside the process (Genesis D).
